# REASONING

Running, chronological reasoning log. Read this before taking over; extend it as reasoning evolves (dead ends and corrections, not just conclusions).

## 2025 — Bootstrap: documentation for the Android port

Goal: port SeedSigner (Python, Raspberry Pi) to Android. Upstream is vendored read-only in `seedsigner_orig/`. This phase is documentation only; no app code yet. The binding requirements live in [docs/spec.md](docs/spec.md); this file records *why*.

### Decisions

| # | Decision | Why |
| - | -------- | --- |
| 1 | **Total isolation** (user constraint): only inputs touch + camera, only output screen | User requirement. Consequences: manifest declares only the camera permission; nothing may open a runtime channel. |
| 2 | **Statelessness** (from upstream, maps 1:1) | Seeds in process memory only; process death wipes them. |
| 3 | **No external dependencies**; vendored source allowed with attribution in `VENDORED.md` (user constraint, refined to allow copy-paste where licenses permit) | Full self-containment keeps the audit surface = this repo. Vendoring a proven QR decoder is cheaper and safer than writing Reed-Solomon from scratch. |
| 4 | **Minimal Google dependency** (user constraint): classic SDK framework only; AndroidX/Jetpack artifacts forbidden unless absolutely required, with the reason recorded here | Baseline: classic Views, `camera2`, plain-file settings — all in the SDK, zero Google artifacts. |
| 5 | Language: Kotlin; `core` module is pure Kotlin with no Android imports | Kotlin stdlib ships with the toolchain (not a dependency). Pure-Kotlin core makes every crypto/QR routine unit-testable on a plain JVM against upstream test vectors. Crypto core sits behind one interface, swappable for Rust later if wanted. |
| 6 | Architecture mirrors upstream MVC: one Activity, one Screen class per upstream View, thin Controller | 1:1 mapping makes the port auditable side by side with the Python original. |
| 7 | All UI is touchscreen; no physical-key assumptions anywhere | The Pi's 4 buttons + joystick have no Android counterpart. |
| 8 | QR decoder: **vendor ZXing** (Apache-2.0) — copy the needed Java source files (QR decode subset only) into `core/` **as-is, no Kotlin rewrite** | Mature, pure Java; Kotlin calls Java 1:1, so a rewrite would only add translation bugs. Trust model (user requirement): the repo is the entire build input — source is here, build happens here, nothing is fetched. `VENDORED.md` pins exact version + SHA-256 of the official release so the copy is verifiable by diff. |
| 9 | Minimum SDK: **API 28 (Android 9)** | `camera2` fully stable, covers the vast majority of devices in use, keeps the API surface small. Revisit only if a real need appears. |
| 10 | Security reports go through **GitHub issues** (user decision); no SLA is promised. Delicate reports stay detail-free in the issue and offer direct contact for the details | **Transparency**: every reported issue is publicly visible to the community; only genuinely sensitive details move to direct contact. A vague report is enough to open the channel. |
| 11 | All binding requirements live in one file: `docs/spec.md` | Constraints were being restated in 5 files and drifting. One source of truth; everything else links to it. |
| 12 | Docs identical to upstream are **referenced**, not copied | QR formats, Electrum, SeedQR, SLIP-0132 are protocol-level and platform-independent. Duplication creates two sources of truth. |
| 13 | Dropped `raspberry_pi_os_build_instructions.md`, `usb_relay.md`, `legacy_hardware.md` | Pure Pi hardware, no Android equivalent. Replaced by `build_instructions.md` and `debug_crash.md` (adb). |
| 14 | `dice_verification.md` keeps upstream screenshots, marked as reference from the Pi build | The fixed inputs and expected outputs (fingerprint, zpub, addresses) are the verification value; they are platform-independent. |
| 15 | `seedsigner_orig/` is read-only | Reference implementation + `tools/mnemonic.py` cross-check. Never edit it. |
| 16 | Removed upstream CI (`.github/`) and `.gitmodules`; rewrote `.gitignore` for Android | They referenced Python packaging, submodules, and paths that do not exist in this repo. CI is re-created at roadmap v0.1 ("CI: build + unit tests"). |

### Decisions (v0.0, implementation phase)

| # | Decision | Why |
| - | -------- | --- |
| 17 | Build toolchain lives in `~/toolchain` (Temurin JDK 17, Android SDK 34, adb, Gradle) — no root | Dev machine has no passwordless sudo; everything the spec allows as toolchain (JDK/SDK/Gradle) installs cleanly into the user home. Kept outside the repo so `git clone` + toolchain stays the only build input. |
| 18 | Build system: Gradle + Android Gradle Plugin (Google first-party, build-time only) | AGP is a build tool, not a runtime artifact: the app's dependency tree stays platform-only per spec §1.3/§1.4. The `./gradlew assembleDebug` flow is already documented in `docs/build_instructions.md`. Kotlin/AGP plugin jars are fetched into the local Gradle cache like any compiler — toolchain, not dependencies. |

| 19 | BIP39 differential testing via `tools/crosscheck_bip39.py` (embit in a dev venv, `~/toolchain/venv`) | spec.md §3 requires differential tests against upstream Python; the tool is committed and re-runnable, the venv is dev-time only and never a build input |
| 20 | Crypto primitives are pure Kotlin on `java.math.BigInteger` (secp256k1 affine, RFC-6979 signing + embit's DER-length grind loop, RIPEMD-160 ported from embit's `py_ripemd160.py`) — no native libs | Spec §1.3 forbids third-party runtime deps. `BigInteger` is JDK, not a dependency. Byte-identity to embit is enforced by `:core:test` (documented vectors from `dice_verification.md`) + the re-runnable crosscheck tool. |
| 21 | **Only very trusted sources** for everything (user constraint): specs, algorithms, test vectors, reference behavior | Memory is not a source. Allowed: the BIP texts + their official test vectors from `github.com/bitcoin/bips` (raw), the embit 0.8.0 source installed in `~/toolchain/venv` (the upstream's own library), Bitcoin Core, RFCs. Anything fetched is checked in-session (e.g. BIP-340/341 were downloaded to /tmp before porting schnorr/taproot). |
| 22 | **Simplest possible solution** in every case (user constraint) | 1:1 ports over clever abstractions; no helper layers, no extra types, no premature generalization. A direct translation of the reference code is the simplest thing that can be audited against it. |
| 23 | **No prebuilt binaries anywhere in the verification path** (user constraint): every artifact we check against must be source code we can read — embit's pure-Python secp256k1 (`embit/util/py_secp256k1.py` + `key.py`), forced in `tools/crosscheck_*.py` via `sys.modules["embit.util.ctypes_secp256k1"] = None` | embit's prebuilt `libsecp256k1_linux_x86_64.so` (2021, secp256k1-zkp build) produces BIP-340 nonces that match *neither* the BIP-340 spec nor any source-fetched zkp revision; its behavior cannot be audited, so it cannot be a byte-identity target. The pure-Python backend is embit's own source and is what our Kotlin is verified against. The `.so` also segfaulted intermittently under ctypes. |
| 24 | **The app must be a drop-in replacement for upstream SeedSigner** (user constraint): identical functionality, flows, and QR protocols, so a wallet user can switch between the Pi device and the APK freely. Android UI: all physical-button interactions become **emulated on-screen buttons**; future stretch goal — draw the SeedSigner case itself on screen (case + buttons + inner screen) for a better emulation feel (roadmap "Beyond") | Upstream's contract *is* the feature spec; divergent behavior would break the replacement promise. The Pi's physical buttons have no Android equivalent other than touch. |
| 25 | The UR2 stack (`core/.../qr/ur2/`: bytewords, crc32, cbor_lite, xoshiro256, random_sampler, fountain_utils, fountain encoder/decoder, UR encoder/decoder) is a 1:1 port of `seedsigner_orig/src/seedsigner/helpers/ur2/`, byte-identity enforced by `tools/crosscheck_ur2.py` + `:core:crosscheck-ur2`. Two upstream quirks are mirrored, not fixed: (a) `cbor_lite.get_byte_length(-5) == 0` so a negative integer encodes as the single byte `tag + value` (invalid CBOR, never used by UR2 parts — asserted in `Ur2RoundTripTest`); (b) `FountainEncoder.partition_message` mutates its fragments, so the reference requires a `bytearray`, not `bytes` | Byte-identity to the reference is the correctness bar (spec §3). "Fixing" an upstream quirk in the port would break identity and hide the diff. Quirks are pinned by tests so a future "cleanup" fails loudly. |
| 26 | QR decoding: ZXing **3.5.4** vendored as **unmodified Java source** (decoder files in `core/src/main/java`; the 11 encoder files moved from test to main for v0.1 — the app renders display QRs from them, while the real QR *encoder* in the ecosystem remains the Python `qrcode` library). Attribution + known-limitation notes in `VENDORED.md`. Real-path verification: `tools/crosscheck_qr.py` + `:core:crosscheck-qr` — Python `qrcode` renders every UR2 part at upstream density sizes (10/30/120 cbor bytes per `encode_qr.py`), the vendored decoder reads them back (277/284; the 7 failures are an upstream ZXing limitation, pinned) | Spec §1.3 allows vendored source with attribution; a Maven ZXing artifact would violate the no-dependencies rule. The decoder must read what upstream *displays* (Python `qrcode` output), not what ZXing itself encodes — hence the crosscheck renders with Python and decodes with the vendored code. |
| 27 | UR crypto payload CBOR (`core/.../qr/ur2/Cbor.kt` + `UrTypes.kt`): 1:1 port of the `urtypes` crypto types (crypto-account/crypto-psbt/crypto-hdkey/crypto-keypath/crypto-coin-info, MIT, commit `7fb280ea` **pinned in upstream's own requirements.txt**) plus the payload-construction logic of `encode_qr.py`. Byte-identity enforced by `tools/crosscheck_urtypes.py` + `:core:crosscheck-urtypes` (10 cases: 84'/49'/48'×3/86'/44'/45'/unknown-48' × main/testnet + crypto-psbt) | The xpub/PSBT QR payloads are part of the drop-in contract (decision 24): a wallet must decode what we display. `urtypes` is upstream's own pinned dependency, so it is a trusted source exactly like embit. No third-party CBOR library is added — the writer is 60 lines and only covers the item types these payloads use. |
| 28 | `app` shell (Chunk B): 1:1 MVC port with one Android-shaped change — upstream's blocking `while True: view.run()` loop becomes an **event-driven loop** (`Controller.runDestination` → `View.run` shows the screen and returns → tap delivers `View.onResult(index)` → next `Destination`). `View` is an `abstract class`; `Ui.screen()` builds a titled screen with back arrow + big buttons; `Controller.showScreen` swaps the content view and wires button/back taps to `onScreenResult`. Same back-stack semantics as upstream (skipCurrentView, clearHistory, BackStackView double-pop, Home wipes flow state). Settings persisted as plain JSON in app-private storage; excluded hardware settings (display/brightness/camera-rotation/persistent-settings/microsd) documented in `Settings.kt` | The main thread cannot block on a `CountDownLatch` — touch events are dispatched by the same looper, so a blocking modal pump deadlocks (the first draft did exactly this). Callback shaping is the only dependency-free way to keep upstream's modal-screen semantics on Android. `Ui.Screen` has no AndroidX: classic `FrameLayout`/`LinearLayout`/`Button`/`TextView` only (spec §1.4). |

### Pitfalls hit

| What was believed | What was true | Rule that prevents the repeat |
| ----------------- | ------------- | ----------------------------- |
| `sdkmanager --sdk_root=~/toolchain/android-sdk` installs into `~/toolchain/android-sdk` | Bash does not tilde-expand `~` after `=`, so packages were installed into a literal directory named `~` under `cmdline-tools/` | Always `$HOME/...` (or a plain variable) in tool arguments, never `~` after `=`. |
| In Kotlin, `a shl 24 or b shl 16` means `((a shl 24) or b) shl 16` | Infix calls (`or`, `and`, `xor`) bind **tighter** than the shift operators (`shl`, `shr`, `ushr`), the opposite of C/Java intuition. The BIP-32 fingerprint came out `9c00ced8` instead of `8d9cced8` while every hash was verified byte-correct | Always parenthesize each shifted term in bit-packing expressions: `((a shl 24) or (b shl 16) or ...)`. Grep rule: `) shl [0-9]+ or` without outer parens is a bug. |
| The secp256k1 general-addition slope was `(y2-y1)/(x1-x2)` | The slope is `(y2-y1)/(x2-x1)`. Every point past 2G was off-curve (detected because `y²≠x³+7`), yet 2G matched the known constant, which hid the bug for a while | After any curve-op change, assert the point is on the curve (`y²≡x³+7`) in tests, not just equality with a constant. |
| For a QNR input, multiplying `a^((p+1)/4)` by `2^((p-1)/4)` recovers the square root | secp256k1 has `p ≡ 7 (mod 8)`, so 2 is a **quadratic residue** and `2^((p-1)/4) ≡ ±1` — the “multiply by sqrt(−1)” trick is a no-op. For valid x the `p ≡ 3 (mod 4)` formula `y = ySq^((p+1)/4)` always works; anything else means x is not on the curve | Compressed-point recovery: compute `y = ySq^((p+1)/4)`, `require(y² ≡ ySq)`, then fix parity. No fallback branch. |
| `BC1QW508D6QEJXTDG4Y5P3AGTQPX9K6KNK9R73V33U` is a BIP-173 valid vector | It fails the bech32 checksum; embit rejects it. Test vectors written from memory are unreliable | Every test vector must be generated/verified against a trusted source (embit, the BIP text) in the same session it is committed. The real BIP-173 v0 vector for program `751e76e8…` is `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4`. |
| BIP-32 serialization: write a key-type prefix byte, then the 33-byte pubkey | The 33-byte compressed pubkey **already contains** its 0x02/0x03 prefix; the layout is 13 + 32 + 33 = 78 bytes. An extra prefix byte overflows the payload | Mirror the BIP-32 byte layout exactly: public → 33 bytes from offset 45; private → `0x00` + 32 bytes. Also reject kind/version mismatch in `serialize` (embit raises `HDError`). |
| The bech32 polymod `chk ^= GEN[i]` per set bit was “wrong” and was “fixed” to `GEN[0]/GEN[4]` | The original matched the BIP-173 reference exactly (embit `bech32.py`); the “fix” broke every checksum. The real failures around it were elsewhere (stale test runs, bogus vectors) | Before changing code to match a spec from memory, diff against the reference implementation on disk (`~/toolchain/venv/.../embit/`) and run a known-good vector through the *unchanged* code first. |
| embit's `.so` BIP-340 signatures were assumed reproducible from spec-standard RFC-6979-style nonces (tried: spec no-aux, aux-zero XOR, zkp source from 3 tags) | The 2021 zkp `.so` uses a nonce scheme that matches none of them; even embit itself re-signing the same (key, msg) through its own API sometimes gave a different sig than the one stored earlier (context/lock-dependent native state), plus intermittent segfaults | Never chase byte-identity against a closed binary. If a reference is not source-readable, it is not a valid target — switch the reference to source (embit's `py_secp256k1` pure-Python backend) and verify against that. |
| A byte-identical crosscheck passing means every code path was exercised | The UR2 crosscheck initially generated only the *minimum* parts (all pure data frames); `choose_fragments` short-circuits for `seq_num <= seq_len`, so the xoshiro256/RNG path was never called. The signed/unsigned bug in `nextDouble()` (Kotlin `Long.toDouble()` is signed; Python `nxt` is unsigned — a high-bit word maps to a negative) was invisible to the crosscheck and only a JUnit test with mixed fountain frames caught it | Differential crosschecks must include cases that force every non-trivial branch (here: generate *more* than the minimum parts so mixed frames use the RNG). A green crosscheck proves only the paths its cases take. |
| `(crc xor b).toInt()` is a valid table index in CRC-32 | The XOR result's low byte has its high bit set ~half the time; `.toInt()` without a `& 0xFF` mask yields a negative index (`AIOOBE: Index -224`). It hid for one compile cycle because single-part decode hit it on the first byte 0xE0 | Any `Long → array index` for a byte-sized value needs an explicit `and 0xFFL` before `.toInt()`. Grep rule: `).toInt()]` preceded by `xor` is suspicious. |
| A `ChecksumException` from the vendored ZXing decoder meant the port was broken | Pristine ZXing 3.5.4 (compiled from the official tag) fails identically. Two separate upstream bugs: (1) the default EC level is **L** and the encoder/decoder pair has an L-only checksum edge case for some contents; (2) a content-dependent detector weakness — a data run near a corner mimics the 1:1:3:1:1 finder ratio, the bottom-left "finder" is detected 33px off, the version is mis-estimated (33 modules sampled on a 37-module QR), and the whole grid is skewed. OpenCV decodes the same PNGs fine | When a vendored library misbehaves, A/B it against the pristine upstream build *before* touching the port: compile the official tag in /tmp and run both on the same input. If pristine fails identically, it is an upstream limitation — document it, pin it in the crosscheck's known-failure set, and mitigate at the app layer (rotation/offset retries). |
| The Python `qrcode` library's `get_matrix()` is row-major `[y][x]` | It is column-major `modules[x][y]`. A scratch script that rendered one matrix as `[y][x]` and another as `[x][y]` produced two PNGs with 19,800 differing pixels (a transpose) from an "identical" matrix, masquerading as an encoder bug | When comparing rendered QRs, compare the PNG pixels, and take the indexing convention from the library source (`qrcode/main.py`), not from intuition. |
| A top-level Kotlin `object Foo { fun main(...) }` is runnable as `FooKt` from a Gradle `JavaExec` | The `<File>Kt` facade class only exists when the file declares top-level functions; an `object` compiles to a class named `Foo`, so `mainClass = "FooKt"` → `ClassNotFoundException` | Crosscheck entry points are top-level `fun main` (same pattern as the other `Crosscheck*.kt`), not objects. |
| `crypto-account` outputs for an unrecognized derivation should list all standard script types | Upstream builds `[Output(tags, key) for tags in outputs]` where `outputs` is an empty list for unknown derivations → `map[2] = []` (an account with zero outputs). And `Output.to_data_item()` tags the inner hdkey map with **303** (crypto-hdkey) *before* wrapping in script tags — dropping the 303 makes the payload structurally unparseable by wallets | For drop-in formats, copy the reference construction code line-by-line (the crosscheck tool does) and let byte-identity tests pin every structural detail, including "boring" ones like empty collections and wrapper tags. |
| An `open class` can hold `abstract fun` members (the `View` base) | Kotlin rejects it: **a class with abstract members must be declared `abstract`**; `open` alone is not enough ("Abstract function 'run' in non-abstract class 'View'"). The error looked unrelated because it cascaded into `Unresolved reference: it` in every subclass file | Abstract base class ⇒ `abstract class`, full stop. When the base class fails to compile, expect nonsense cascade errors (`it` unresolved) in every subclass — fix the base first, re-read the remaining errors. |
| `val pendingSeed: Seed?` plus `fun getPendingSeed(): Seed?` can coexist in a Kotlin class | They collide at the JVM level: the property's generated getter and the function have the same signature → `Platform declaration clash`. Python's attribute/method split has no Kotlin equivalent | Don't name a function `getX` when a property `x` exists (its getter is `getX`). Use a distinct name or rely on the property. |
| The platform `android.jar` (API 34, installed via `sdkmanager` into `~/toolchain`) has the usual API: `TextureView.getSurface()`, `DisplayMetrics.getMinDimension()` | This build's stub jar is **stripped**: `View.getSurface()` (API 30+) and `DisplayMetrics.getMinDimension()` are absent, so references to them fail with `Unresolved reference` while most of the API works. Verified by `javap` against the jar itself | When a platform API is "unresolved", verify with `javap -cp <android.jar>` before assuming a typo; if the stub lacks it, use an equivalent older API (here: `Surface(preview.surfaceTexture)`, `minOf(widthPixels, heightPixels)`). |
| The vendored ZXing `PlanarYUVLuminanceSource` supports a `rotation` constructor parameter like modern ZXing | The vendored 3.5.4 copy has the **old** constructor `(data, w, h, left, top, w, h, boolean reverseHorizontal)` — no rotation. Also `HybridBinarizer` and `MultiFormatReader` are **not in the vendored set**; the proven decode path is `QRCodeReader().decode(BinaryBitmap(GlobalHistogramBinarizer(source)))` (what `ZxingDecodeTest` uses) | Before using a vendored library's API, grep the vendored source for the exact signature — vendor sets can be partial and older than the upstream release implies. Frame rotations for the detector sweep are done by re-packing the Y plane. |
| `getDeclaredConstructor().newInstance()` can instantiate any View, like Python's `View_cls()` | Python's `View_cls(**view_args)` passes keyword args to `__init__`. Kotlin/Java reflection needs the matching constructor AND its parameter names, which only exist in the class file when compiled with `-java-parameters` | `app/build.gradle.kts` sets `freeCompilerArgs += "-java-parameters"`. (Superseded by the 2026-07 audit entry below, which found the "no no-arg constructor" belief in the next row WRONG: Kotlin DOES emit an implicit no-arg ctor when every param is defaulted, and both the old exact-match matcher and a naive kwargs matcher silently used it.) |
| `String.dropLast()` compiles like everywhere else | In this toolchain it fails with `No value passed for parameter 'n'` (cause not pinned down; the app module's stdlib resolution resolved `dropLast` without its default) | Use `substring(0, length - 1)` for one-char trim in the app module. Recorded so a future instance doesn't burn time re-diagnosing. |
| `Networks.fromName("main")` works because embit's network keys are "main"/"test"/"regtest" | `fromName` only accepted the full names ("mainnet"), so every app-side `getFingerprint`/`deriveXpub` call threw `IllegalArgumentException: unknown network: main` at runtime. The core tests never exercised the app's mapping, so it went unnoticed until the first `:app:testDebugUnitTest` | `fromName` now accepts both forms. Rule: when two layers map the same concept (setting value → embit key → Networks enum), add a unit test that runs the full chain end-to-end, not just each layer alone. |
| `viewArgs` values of type `String?` can't be passed to a constructor parameter declared `String?` via `getDeclaredConstructor` | They can — `Constructor.newInstance(null)` is fine for nullable Kotlin params (they compile to object refs). The real constraint is the exact key/name match in `Controller.instantiateView`: every parameter of the chosen constructor needs a viewArgs key, so viewArgs maps must always carry all keys (e.g. `customDerivation to null` even when unused) | When a View has an optional upstream parameter (like `custom_derivation: str = None`), keep it as a constructor parameter and always pass the key from every call site. |
| The PSBT `master_fingerprint` field is little-endian, like every other integer in the BIP-174 binary format | It is the first 4 bytes of the hash160 **in their natural order**, which is the big-endian encoding of the int value (e.g. fingerprint int `0x0fb882ff` → bytes `0f b8 82 ff`). Using `intToLe4` for it made every fingerprint compare fail, so the parser rejected every psbt with `PsbtSeedCannotSignError` | `Psbt.kt` has both `intToLe4` (derivation indices, tx fields) and `intToBe4` (fingerprints). Fingerprint comparisons always go through `intToBe4(root.myFingerprint)`. |
| A PSBT's global xpubs are bare 33-byte public keys, so `HDKey.fromPublicKey(bytes)` can build them | BIP-174 serializes them as full 34-byte BIP-32 payloads, and embit stores `psbt.xpubs` keyed on `HDKey.parse(...)` objects. Feeding the 34 bytes to `fromPublicKey` hits `require(publicKey.size == 33)`; cosigner resolution silently failed (the exception is swallowed by `_get_policy`'s bare `except`, exactly like upstream) | `Bip32.HDKey.parseBytes(payload)` was added for the raw 78-byte form; `getCosigners` uses it. Rule: when a lookup "silently" returns nothing, check whether the caller swallows exceptions upstream also swallows — the failure is inside, not in the comparison. |
| embit's `script.p2tr(key)` builds a plain `OP_1 OP_32 <x-only>` of the given key | It **tweaks** the internal key with the (empty) script tree first: `output_key = pubkey.taproot_tweak(tweak)`. Rebuilding the change scriptPubKey without the tweak never matched, so every honest taproot change output was misclassified as an external spend | The p2tr branch of `PsbtParser.parseOutputs` rebuilds with `Script.p2tr(Secp256k1.taprootTweakPub(internalKeyXOnly))`. The raw-key `Script.p2tr` factory remains for display/parsing purposes only. |
| `PSBTParser(p, seed, network)` parses lazily; you call `parse()` afterwards | Upstream's `__init__` calls `self.parse()` itself when a seed is given, so verification exceptions (ownership claims, mixed path types, cannot-sign) are thrown **by the constructor**. The Kotlin port mirrors this, and the crosscheck originally tried to catch the exception from a second `parse()` call and missed it | Wrap `PsbtParser(...)` construction in the try/catch when an exception is expected. The fields are only meaningful if construction succeeded. |
| `Map.entries` iteration lets you mutate `entry.value` in Kotlin | `Map` is declared `Map<out K, out V>`, so `entries` resolves to `Set<Map.Entry<K,V>>` with a **read-only** `value` ("Val cannot be reassigned") even when the map is a `MutableMap` | Rebuild the map and `clear()` + `putAll()` (content-equality keys like `ByteArray` make key-lookup replacement impossible anyway). See `fillMissingFingerprints` in `PsbtParser.kt`. |
| Python `list[-1]` works everywhere, so the port can pass `-1` to Kotlin list code | Kotlin throws `ArrayIndexOutOfBoundsException` on negative indices; upstream `update_pending_mnemonic(word, -1)` means "final slot" | `SeedStorage.updatePendingMnemonic` normalizes negative indices like Python. When porting a call site that uses `-1`, port the semantics, not just the literal. |
| A view constructor with all-default params (`View(a: Int = 0, b: Boolean = false)`) can be instantiated via `getDeclaredConstructor()` or a partial `viewArgs` map | Kotlin 1.9 (with `-java-parameters`) actually generates THREE ctors: a real no-arg ctor, the full N-param ctor with real names, and synthetic defaulting bridges named `arg0/arg1/...` (dumped in 2026-07). The no-arg ctor made the old exact-count matcher's fallback "work" — by silently dropping every viewArg and leaving constructor properties at defaults (the SeedWordsWarningView/`seedIndex` E2E NPE). The "no no-arg ctor exists" belief that motivated the "pass every key from every call site" rule was wrong | `Controller.instantiateView` now mirrors Python kwargs: use the named ctor whenever every viewArgs key is one of its params; an ABSENT key is tolerated only for reference-type parameters (nullable Kotlin params, whose defaults are null) — an absent key for a non-null `Int`/`Boolean` (primitives) falls back to the no-arg ctor. `ViewInstantiationTest` pins the invariant (≤1 named ctor per View; add every new View class to its list) and the kwargs binding itself. Keeping the full-key call-site habit is still correct and makes intent explicit. |
| `android.os.Looper.getMainLooper().post { ... }` compiles on any normal Android toolchain | This stripped platform stub's `Looper` has no `post` (`Unresolved reference: post`) | Post through `Handler(Looper.getMainLooper()).post { ... }` — same call the full SDK resolves to. |
| A `Bitmap` can be added straight to a layout | `Bitmap` is a `Drawable`, not a `View` — `LinearLayout.addView(Bitmap, ...)` fails with "None of the following functions can be called" | Wrap in an `ImageView` (`scaleType = FIT_CENTER`, `setImageBitmap`). |
| `0xFF000000` is an Int literal | Kotlin promotes hex literals beyond `Int.MAX_VALUE` to **Long**; `0xFF000000 or x` (x Int) is a type mismatch | Write `0xFF000000.toInt()`. (Same family as the existing color-literal `.toInt()` usages throughout the app views.) |
| Upstream image-entropy inputs can be ported literally (CPU serial, RGB frames, PIL autocontrast) | Android exposes no `/proc/cpuinfo` serial; the camera2 stream here is YUV_420_888 (no RGB); PIL is a third-party dep (spec §1.3) | Documented platform mapping in `ToolsViews.kt`: `Settings.Secure.ANDROID_ID` (no permission, per-device uniqueness — same role) for the serial, packed Y planes for frames (same sensor data, entropy role unchanged), raw-frame display in place of the contrast-boosted copy (the boost never affected entropy). The sha256 chain structure is 1:1. |

### Decisions (v0.3/v0.4, address verification → descriptor → seed flows)

- **Address verification / explorer / descriptor / SeedQR / Electrum / SettingsQR are all ported 1:1** (commits `6d3f0f5` → `90b7afb`). The v0.3 roadmap is complete except on-device E2E; v0.4's remaining scope was multi-key signing + Electrum + SettingsQR — all now in.
- **Descriptor model lives in `core/descriptor/Descriptor.kt`**: basic-multisig subset of embit 0.8.0 (`AllowedDerivation`, `Key`, `Multi`/`Sortedmulti`, `Descriptor.fromString`, `derivedScriptPubkey`, `owns`), plus `getMultisigAddress`/`getMultisigPolicy`. Crosscheck `:core:crosscheck-descriptor` pins it at **96/96 byte-identical** (addresses, policy, owns, malformed rejects).
- **Specter animated QR accumulation uses a companion object** (`ScanWalletDescriptorView.segments`): each frame re-runs the view (fresh camera) but collected segments survive — the touch equivalent of upstream's collector thread. `fresh=true` on first entry resets it.
- **Seed class hierarchy** (1:1 of `models/seed.py`): `abstract class Seed` → `Bip39Seed` (default) / `ElectrumSeed`. Electrum: 12 words, version prefix `100` (HMAC-SHA512 "Seed version"), `PBKDF2WithHmacSHA512(mnemonic, "electrum"+passphrase, 2048)`, script override native_segwit, derivation `m/0h`/`m/1h`, `isStandard=false` (excluded from PSBT signing). The Electrum passphrase is lowercase+whitespace-collapsed and NOT NFKD-normalized before the PBKDF2 salt (upstream quirk kept).
- **SeedQR transcription** is the full upstream chain (Format → Warning → WholeQR → ZoomedIn → Confirm). ZoomedIn renders the QR oversized (24 px/module, 4-module border) and draws zone guidelines with plain `setPixel` helpers (the platform stub has no `Bitmap.drawVerticalLine`); it scales a 5-module-zone view. Confirm-scan accepts numeric (48/96 digits), compact-bytes (`ur.type=="bytes"` → `Bip39.mnemonicFromEntropy`), or plain 12/24-word strings.
- **Vendored ZXing gained a byte-mode encoder path** (`Encoder.encodeBytes` + `QRCodeWriter.encodeBytes`): the string pipeline was split into `buildQrCode`/`finishAndReturn` helpers so the byte path reuses version selection, EC, masking and matrix building. String output is unchanged (all QR crosschecks still green). Documented in `VENDORED.md` per the no-silent-modification rule.
- **SettingsQR** (`SettingsQr.parse`): 1:1 of upstream `Settings.parse_settingsqr` — `settings::v1`, optional `name=`, abbreviated names, `,`-split multi-values with int coercion, unknown attrs ignored, invalid values raise. `denomination` uses full names (`btc`, `sats`), unlike the app setting's single letters — the parser validates against the settings entries, so test vectors must use `denom=btc`.

### Pitfalls hit (v0.3/v0.4)

| What was believed | What was actually true | Rule that prevents the repeat |
|---|---|---|
| A KDoc comment mentioning `/0/*` is safe | Kotlin **block comments nest**: the `/*` inside `/0/*` opens a nested comment and swallows the rest of the file (`Unclosed comment` at EOF) | Never write `/*` or `*/` inside `/**` KDoc; spell it out ("zero branch, any index"). |
| `"text" to e.message ?: "fallback"` builds a map entry with a fallback | `to` binds tighter than `?:` — this is `("text" to msg) ?: "fallback"`, an `Any` that breaks `mapOf` typing | Parenthesize: `"text" to (msg ?: "fallback")`. |
| `String.all { ... }` exists like `Iterable.all` | It does not — `all` with a predicate is Iterable/sequence-only; `"," in value` also needs the receiver typed as String when `value` is `Any` | For strings: `s.all { it.isDigit() }` after an explicit `as String` (or `.let`). |
| An overriding fun may repeat the base default arguments | Kotlin error: "An overriding function is not allowed to specify default values" | Defaults live only on the base declaration. |
| `protected var seedBytes; private set` + subclass assignment works | The `private set` is private **to the base class**; subclass writes fail. `lateinit`+`private set` also fails ("Property must be initialized or be abstract") | Use `var seedBytes: ByteArray = ByteArray(0); protected set` (plain protected setter). |
| A subclass `init` block runs before the base class's `_generateSeed()` hook | Kotlin runs the **base init first**, calling virtual `_generateSeed()` while subclass properties are still unset (UninitializedPropertyAccessException) | Subclass state read by a base-init hook must be a computed property (getter recomputes from base state); re-run the generation in the subclass `init`. |
| The vendored ZXing `QRCodeWriter.encode` has a `byte[]` overload like upstream ZXing | This 3.5.4 vendored copy's writer takes `String` only (the upstream Java API has both) | Grep the vendored source for the exact overload before calling it; add + document a modification when it's genuinely missing (compact SeedQR needed byte mode). |
| `BitArray.append(int, int)` exists | The method is `appendBits(int, int)` | Read the vendored `BitArray` API; names are not the same as every other port. |
| Upstream `ToolsCalcFinalWordDoneView` "Load seed" goes to `SeedFinalizeView` — already correct in the port | It was pointed at `SeedDiscardView` in one branch and `SeedFinalizeView` in another after a blind `sed`; upstream: LOAD → `SeedFinalizeView` (pending seed kept for passphrase), DISCARD → `SeedDiscardView` | After any bulk `sed`, re-read the changed hunk in context; verify each routing against the upstream file, not against memory. |
| Electrum seeds validate like BIP-39 (`validateMnemonic` → `Seed(mnemonic)`) | `Seed` is now abstract; validation and pending→seed conversion must pick the subclass from `SeedStorage._pendingIsElectrum` | Every place that constructs a seed from words now routes through the pending-mnemonic state (which knows the flavor), or an explicit `Bip39Seed`. |
| `Controller.instantiateView` (reflection) found the right constructor whenever viewArgs and the constructor had the same number of names | An EXACT size+names match silently fell back to the no-arg constructor whenever a call site passed a partial key set (e.g. `SeedBackupView` → `SeedWordsWarningView` with only `seedIndex`; 4-param constructor). All constructor properties were then null → NPE deep in the flow (`SeedWordsView.run`, `activeSeed()`). It looked like a seed-ownership bug; it was an instantiation bug | The matcher now uses Python-`**kwargs` semantics: the most specific constructor whose parameters are ALL named in viewArgs (extras ignored), no-arg as fallback. Never add a view constructor param without passing it from every constructing call site or proving the fallback can't be hit. The JVM-level flow (destination → viewArgs → instantiated view) is testable in a plain unit test — do it when touching this path. |
| "DISCARD → `SeedDiscardView`" matched upstream, so the routing is 1:1 | Upstream's `SeedDiscardView` has a **pending-seed mode** (`seed=None` → `is_pending_seed`, wipes `pending_mnemonic`); our port only implements the `seedIndex`-into-loaded-seeds form. The calc-final-word "Discard" therefore offers to delete the first *loaded* seed (or crashes when none) instead of dropping the pending mnemonic | Porting a *routing* is not the same as porting the *target*: when a Destination points at a view whose upstream constructor has an optional identity parameter, port the whole parameter space, and exercise both branches in E2E. (Found in the full-repo audit; see docs/current-task.md A1.) |
| A view's `viewArgs` is available to property initializers, like any other field, once the object exists | `Controller.runView` instantiates the View FIRST and assigns `view.viewArgs` AFTER. A plain property initializer (`private val x: Int = viewArgs["x"] as Int`) therefore always sees the EMPTY map. `SettingsMenuView.visibility` silently kept its default (tapping "Advanced" re-pushed the General menu forever); `QrDisplayView.parts`/`SettingsEntryUpdateView.attrName` would NPE on first use. It only surfaced on device — no unit test constructs views the way the Controller does | View constructor params are the ONLY reliable way to receive viewArgs at construction (instantiateView binds them); anything else must be read in `run()`/`onResult()` or via `by lazy`. A guard comment now lives on `View.viewArgs`. Grep rule: `= viewArgs[` on a `val` line is a bug unless it's `by lazy`.
| The tap-by-tap `adb shell input tap` keyboard entry is lossy (candidate-suggest taps occasionally pick the wrong word), so an on-screen seed entry cannot be trusted to reproduce an exact mnemonic | The fingerprint screen rendered different (both valid) fingerprints across runs of the "same" entry — the entry itself varied, not the crypto | For E2E, verify rendering + flow, and cross-check any crypto-dependent value (fingerprint) against the mnemonic the app actually holds (read it back via the View seed words screen + uiautomator text dump), not against the mnemonic that was intended. |
